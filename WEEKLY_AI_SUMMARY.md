# Weekly AI summary

The admin panel requests one summary for a completed reporting week (the stored Sunday `endDate` represents the preceding Sunday–Saturday). All active students' check-ins for that week are included, independent of UI filters. Only the latest record per member is used; Trash is excluded. The model receives pseudonymous source labels, check-in answers and six metrics, not roster names, shop names, member IDs or private admin notes. Free-text answers may themselves contain personal or sensitive information. Review consent and Cloudflare data processing terms before enabling.

The production configuration includes the owner-approved Workers AI binding named `AI` and the Worker variable `ENABLE_WEEKLY_AI` set to the string `true`. No records are sent until an admin clicks Generate summary. The model is `@cf/meta/llama-3.3-70b-instruct-fp8-fast`. Leave the flag unset to disable. No API key is required by this binding. Existing deployments remain functional without it.

The on-demand POST `/api/admin` action `weeklySummary` requires a current admin session, same-origin JSON and a valid Sunday `week`. Maximum 200 students / 90,000 input characters, no silent truncation, 3,200 output tokens, a 45-second application timeout, bounded structured output and validated source references. Requests are limited to 20 uncached generations per 15 minutes across admins using the existing D1 rate limiter. A best-effort, database-scoped in-memory cache reuses identical source fingerprints for 15 minutes (maximum 12 items); isolate restarts or changing binding identity can miss it. It is not durable. The upstream AI call may continue after application timeout.

Source text is untrusted JSON in a user message; the fixed system prompt explicitly rejects embedded instructions. No tools, external navigation or secrets are available to the model. This limits but cannot eliminate prompt injection or hallucination. Every returned item must have valid source references; this does not prove semantic accuracy. Admins should open the cited check-ins and verify claims. Invalid output, unavailable AI and provider failures are errors, never fabricated fallback summaries.

UI integration: `WeeklySummary` from `src/weekly-summary.tsx` accepts `week`, `revision` (use `data.entries` to invalidate changed data), and `onSource(checkinId)` to navigate to the original record. Selection/source changes unmount and abort the old request, preventing stale results. No request is sent until Generate is clicked.

Legacy reporting periods: summaries query the selected Sunday and its preceding Saturday. Sunday-cycle records are included only at the selected Sunday; legacy records are included only at the preceding Saturday, so both represent the same Sunday–Saturday interval. Incompatible records in those candidate dates are excluded and counted in `excludedCount` (also returned for `no_data`). Latest-per-member selection occurs after this interval filter. Cache hits return the current excluded count.

## Check-in follow-up

The admin panel compares the latest saved timestamp across all active records against a rolling 14-day cutoff. Edits count as activity, independently of the reporting week. Exactly 14 days is still inside the window. Trash is excluded; members with no active check-in are listed separately rather than assumed overdue. Missing, invalid or future timestamps are flagged for review. The panel shows Central-time dates and fetches new records with Refresh.


Name variants are grouped only in the admin follow-up display. Case, accents, apostrophes, punctuation, spacing and last-name-first formatting are normalized. Matching full names may span shops. First-name-only, initials, compatible middle names or a one-letter edit/transposition require the same normalized shop for automatic matching. Every pair in a candidate group must match; ambiguous initial/first-name/typo chains stay separate. Similar names at different shops are shown as possible matches without changing their status. Nicknames and unrelated short names are not guessed. The newest active saved timestamp across an accepted group controls follow-up, and each group counts once. Matched names and possible matches remain visible with links to original records. This is a heuristic for admin follow-up, not identity verification: no database records, member access, roster metrics, notes or AI summaries are merged or changed.
